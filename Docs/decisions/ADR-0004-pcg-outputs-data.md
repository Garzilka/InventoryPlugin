# ADR-0004: PCG отдаёт данные, раскладку структур передаёт сервер

- **Дата:** 2026-10-26
- **Статус:** принято
- **Связано:** [03-pcg-contract.md](../03-pcg-contract.md), [02-data-contract.md](../02-data-contract.md)

## Контекст

PCG необходим: композиция зданий, промзон, военных объектов должна быть сложной и непохожей.
Но в мультиплеере объекты должны совпадать у клиента и сервера и иметь общие ID. Если каждый
спавнит объекты у себя, «дверь ангара №87» не существует как общий объект.

## Варианты

1. **PCG спавнит актёров** на обеих сторонах; синхронизация по позиции/имени.
2. **Обе стороны считают раскладку** независимо, синхронизация хешами.
3. **Граф отдаёт данные**, раскладку структур считает сервер и присылает клиенту данными;
   клиент по ней строит внешний вид через PCG.

## Решение

**Вариант 3.**

- Сервер: композиция структур → записи `{kind, pos, yaw, variantSeed, flags, id}` → клиенту.
- Клиент: по записям + `variantSeed` строит внешний вид и мелкий декор.
- Интерактив (двери, контейнеры, лут) — репликация состояния, ID общие.
- Декор (трава, листва, камни) — клиент локально, никуда не передаётся.

## Следствия

- ✅ Статика (стены) гарантированно совпадает с коллизией сервера — нет «невидимых стен».
- ✅ PCG сохраняет всю мощь для «как выглядит».
- ✅ Надёжность не зависит от идеальности детерминизма PCG.
- ⚠️ Трафик: килобайты на участок с застройкой (приемлемо).
- ⚠️ Графы PCG обязаны уметь принимать раскладку как вход (`UPCGStructureInput`).
- ⚠️ Декор всё равно должен быть детерминированным, если он влияет на геймплей
  (например, кусты, за которыми можно спрятаться).
