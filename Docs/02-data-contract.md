# 02. Контракт данных

**Статус:** 🟡 черновик v1 (точная побайтовая раскладка фиксируется при первом коде)

Документ отвечает на вопросы: что такое генплан, что лежит в данных участка, в каких единицах,
как проверяется целостность и какие у всего этого бюджеты.

---

## 1. Общая картина

```
СИД + версии
     │
     ▼
 ГЕНПЛАН (WorldDNA) ─── маленький, один на мир
     │  размер мира, регионы, гидрограф, дорожный граф, поселения, промзоны, POI
     │
     ├──────────────► СЕРВЕР: раскладка структур по участкам ──► клиенту (данные)
     │
     ▼
 УЧАСТОК (ChunkData) = ФОРМУЛА(генплан, cx, cy)   ← считается независимо, параллельно
     │  высоты, маски, грунт, раскладка структур, хеш
     │
     ▼
 ПРАВКИ ИГРОКОВ (Tier C) = отдельное хранилище, накладывается ПОСЛЕ генерации
```

## 2. Единицы и координаты

| Понятие | Правило |
|---|---|
| Система координат | Метры, **X — восток, Y — север, Z — вверх** |
| Внутреннее представление | `int32` в **сантиметрах** (±21 474 км — с запасом) |
| В данных на диске | `uint16` (высоты — смещение от минимума мира), `int32` для позиций |
| Углы | `uint16`, где 65536 = 360° |
| Участок | 256 × 256 м, индекс `(cx, cy)`, покрывает `[cx·256, (cx+1)·256) × [cy·256, (cy+1)·256)` |
| Начало координат | Фиксировано в мире (0,0) и **не зависит от размера мира** — иначе при смене размера поехали бы все индексы |
| Участок (0,0) | Левый-нижний угол в (0, 0); индексы могут быть отрицательными |
| Сэмпл `(i, j)` | Точка `x = cx·256 + i`, `y = cy·256 + j`, `i, j ∈ 0…256` |
| Соседние участки | Дублируют граничный ряд сэмплов (257-й ряд совпадает с 0-м рядом соседа) — это гарантирует **бит-идентичные** высоты на стыке |

### 2.1 Высоты

Генплан объявляет **глобальный** диапазон высот мира: `minZ_cm`, `maxZ_cm`, `heightUnitCm`
(1 или 2 см на единицу хранения).

```
хранимое_значение = (z_cm − minZ_cm) / heightUnitCm     // uint16, 0…65535
z_cm              = minZ_cm + хранимое_значение · heightUnitCm
```

- При диапазоне 0…655 м и единице 1 см — точность 1 см, этого достаточно.
- Нужен больший перепад — генплан ставит `heightUnitCm = 2` (диапазон 1310 м, точность 2 см).

> ⚠️ **Никогда не нормализовать высоты по каждому участку отдельно.** Это создаёт ступеньки
> на границах участков. Только глобальная линейная карта из генплана.

## 3. Генплан (WorldDNA)

| Поле | Тип | Назначение |
|---|---|---|
| `seed` | `uint64` | Сид мира |
| `formatVersion` | `uint16` | Версия формата |
| `generatorVersion` | `uint64` | Версия формул генерации |
| `graphVersion` | `uint32` | Версия графов PCG |
| `assetVersion` | `uint32` | Версия ассетов, влияющих на раскладку |
| `worldSizeChunksX`, `worldSizeChunksY` | `int32` | Размер мира в участках (может быть разным) |
| `originChunkX`, `originChunkY` | `int32` | Индекс участка, считающегося «центром» мира (спавн, карта) |
| `minZ_cm`, `maxZ_cm`, `heightUnitCm` | `int32`, `int32`, `uint8` | Глобальный диапазон высот |
| `regions[]` | массив | Макро-регионы: тип (горы/холмы/низина/пойма), центр, радиус/полигон, параметры |
| `hydrology` | блок | Реки и озёра (см. 3.2) |
| `roads` | блок | Дорожный граф (см. 3.3) |
| `settlements[]` | массив | Посёлки и города: центр, радиус, тип, плотность, оси улиц |
| `zones[]` | массив | Промзоны, военные объекты, карьеры: тип, якорь (привязка к дороге), размер |
| `pois[]` | массив | Точки интереса: лагерь, блок-пост, вышка, ферма |
| `hash` | `uint64` | Хеш всего генплана (от канонической сериализации) |

### 3.1 Каноническая сериализация

- little-endian, без выравнивающих «пустых» байтов;
- массивы — в порядке возрастания `id` (никакого «порядка создания»);
- строки — только как индексы из таблицы строк в начале блока;
- дробных чисел нет вообще.

Только так `hash` будет одинаковым у клиента и сервера.

### 3.2 Гидрограф (`hydrology`)

| Поле | Тип | Назначение |
|---|---|---|
| `nodes[]` | массив | Истоки, слияния, устья, выходы озёр: `id`, позиция (см), тип |
| `rivers[]` | массив | `id`, узлы `from→to`, полилиния, ширина, глубина русла, уровень воды, профиль дна |
| `lakes[]` | массив | `id`, полигон, уровень воды, глубина, выход (узел или «замкнутый бассейн») |

Река обязана **монотонно понижаться** от истока к устью — это проверяется валидатором
(см. `docs` шага 6). Иначе получим «реку в гору».

### 3.3 Дорожный граф (`roads`)

| Поле | Тип | Назначение |
|---|---|---|
| `nodes[]` | массив | Развилки, повороты, въезды: `id`, позиция, тип (перекрёсток/примыкание/тупик) |
| `edges[]` | массив | `id`, класс (магистраль/грунтовка/дворовая/техническая), `from→to`, полилиния, ширина, профиль высот |
| `bridges[]` | массив | Мосты и трубы: `id`, ребро, участок, тип, габариты, высота над водой |

### 3.4 Бюджет размера

Целевой бюджет — **до 500 КБ** на мир 16 × 16 км. Если выходит больше: упрощать полилинии
(шаг 4–8 м) и переходить на компактные структуры. Генплан передаётся клиенту **один раз**
при подключении.

## 4. Данные участка (ChunkData)

### 4.1 Заголовок

| Поле | Тип | Значение |
|---|---|---|
| `magic` | 4 байта | `UWG1` |
| `formatVersion` | `uint16` | |
| `generatorVersion` | `uint64` | |
| `cx`, `cy` | `int32` | Индекс участка |
| `sizeMeters` | `uint16` | 256 |
| `heightStepCm` | `uint16` | 100 (шаг сетки высот, 1 м) |
| `sampleCount` | `uint16` | 257 |
| `minZ_cm`, `maxZ_cm` | `int32` | Копия из генплана (для самопроверки) |
| `heightUnitCm` | `uint8` | |
| `flags` | `uint32` | Биты: есть грунт, есть раскладка, есть вода, … |
| `hash` | `uint64` | Хеш содержимого участка |

### 4.2 Блоки данных

| Блок | Размер | Содержимое |
|---|---|---|
| `heights` | 66 049 × 2 Б ≈ **129 КБ** | Высоты `uint16`, шаг 1 м, 257 × 257 |
| `masks` | 4 × 66 049 × 1 Б ≈ **258 КБ** | Лес, камень, грязь (визуальная), «можно копать/строить» — шаг 1 м |
| `soil` *(резерв)* | 16 641 × 3 Б ≈ **49 КБ** | Грунт для техники: тип, толщина (0–25 см), влажность. Шаг 2 м. Используется только на этапе техники (см. `05-mud-and-vehicles.md`) |
| `structures` | переменный, обычно 0–6 КБ | Раскладка: что где стоит (см. 4.4) |
| `hash` | 8 Б | Хеш блоков |

Итого типичный участок ≈ **440 КБ**. 25 загруженных участков ≈ 11 МБ данных.

> ℹ️ Почему маски на 1 м, а грунт на 2 м: маски нужны для плотной растительности и точного
> копания русел, а грунт меняется медленно — 2 м достаточно и вдвое дешевле.

### 4.3 Семантика масок

| Маска | 0 | 10000 (1.0) | Кто использует |
|---|---|---|---|
| Лес | нет леса | чаща | Расстановка деревьев, покраска |
| Камень | земля | монолитная скала | Камни, проходимость, покраска |
| Грязь (визуальная) | сухо | жидкая грязь | Покраска, скорость пешехода |
| Разрешение копать/строить | запрещено | свободно | Русла, полотно дорог, площадки зданий |

> ⚠️ Маска — это **источник правды на CPU**. RVT (текстура на видеокарте) — только изображение
> масок. PCG и все решения читают маску, не RVT (см. `03-pcg-contract.md`).

### 4.4 Раскладка структур (`structures`)

Одна запись = один объект:

| Поле | Тип | Назначение |
|---|---|---|
| `kind` | `uint16` | Тип (дом, ангар, склад, блок-пост, забор…) |
| `posX`, `posY`, `posZ` | `int32` (см) | Позиция |
| `yaw` | `uint16` | Поворот |
| `variantSeed` | `uint32` | Сид варианта внешности (крыша, окна, двери) |
| `flags` | `uint16` | Состояние побитово (дверь есть, забор ломаемый и т.д.) |
| `id` | `uint64` | Постоянный ID = `Hash64(seed, cx, cy, kind, localIndex)` |

Запись ≈ 24 байта. Плотный город на участок (≈ 250 объектов) ≈ 6 КБ.

**Почему раскладка приходит с сервера, а не считается клиентом:** если клиент нарисует стену,
которой на сервере нет, игрок упрётся в невидимую стену или пройдёт сквозь видимую. Передача
данными гарантирует совпадение по построению (см. ADR-0004).

## 5. Состояния участка (не сохраняются, живут в памяти)

```
НЕТ  →  ДАННЫЕ ЕСТЬ  →  КОЛЛИЗИЯ ГОТОВИТСЯ  →  ГОТОВ
```

| Состояние | Что можно | Что нельзя |
|---|---|---|
| `НЕТ` | — | Всё |
| `ДАННЫЕ ЕСТЬ` | Показать меш (если есть) | Пускать игрока, спавнить объекты, строить |
| `КОЛЛИЗИЯ ГОТОВИТСЯ` | Рисовать | Пускать игрока |
| `ГОТОВ` | Всё | — |

Правило: **игрок и логика входят только в `ГОТОВ`**. Это защита от провала в мир во время
асинхронной готовки физики.

## 6. Правки игроков (Tier C)

Хранятся **отдельно от процедурных данных** — в базе сервера, не в файле участка.

| Тип правки | Содержимое |
|---|---|
| Деформация рельефа | Пятно: позиция, радиус, изменение высоты (см) |
| Деформация грунта (колея) | Пятно: позиция, радиус, глубина, тип грунта — этап техники |
| Снятый/поставленный объект | `id` объекта, новое состояние |
| Состояние интерактива | `id`, открыт/закрыт, прочность, содержимое, владелец |
| Постройка игрока | Тип, позиция, поворот, автор, время |

Правила:

1. Правки накладываются **после** генерации: `итог = сгенерировано + правки`.
2. Правки не могут менять генплан (нельзя «передвинуть реку»).
3. Правки применяются в каноническом порядке (по времени, затем по `id`) — чтобы результат был
   воспроизводимым.
4. Размер: одна правка ≈ 16–32 байта; миллион правок ≈ 30 МБ. Растёт от активности игроков,
   а не от размера мира.

## 7. Радиусы и бюджеты

| Параметр | Значение | Зачем |
|---|---|---|
| Радиус визуала | 2000–3000 м | Дальность прорисовки (степь + туман) |
| Радиус физики | 400–600 м | Коллизия рельефа нужна только рядом |
| Радиус ИИ / проходимости | 128–256 м | Самая дорогая часть |
| Высоты + маски на участок | ≤ 3–5 мс | Воркер-поток |
| Сборка меша участка | ≤ 8 мс | Воркер-поток |
| Готовка коллизии (сетка 2 м) | ≤ 10 мс | Фоновая задача |
| Граф PCG на участок | ≤ 3 мс | Только клиент |
| Бюджет кадра на стриминг | ≤ 2–4 мс | Не более 1–2 участков за кадр |

## 8. Открытые вопросы (закрываются по ходу шагов 4–9)

1. Точная побайтовая раскладка блоков — фиксируется при первом коде.
2. Формат полилиний рек/дорог: шаг точек, сглаживание, профиль высот (шаги 6–7).
3. Нужен ли отдельный блок «вода» на участке (уровни, глубина) или всё берётся из генплана.
4. Правила размещения регионов и зон (шаг 8).
5. Как хранить правки игроков по участкам для быстрой выборки (шаг 12).
