# 03. Контракт PCG

**Статус:** 🟡 черновик v1 (требует проверки кодом — см. «Спайки» в конце)

PCG (Procedural Content Generation) в UE5 — визуальный граф правил, которым мы расставляем
объекты: здания внутри промзоны, деревья по маске леса, камни по маске камня, подстилку у воды.

Документ отвечает на вопрос: **как использовать PCG, чтобы он не ломал одинаковость мира**.

---

## 1. Роль PCG: композиция, а не решение

| Что PCG решает | Что PCG НЕ решает |
|---|---|
| Как выглядит ангар из типа «ангар» + сид варианта | Где стоит ангар |
| Как расставить деревья по маске леса | Где находится лес |
| Где внутри промзоны склады, цистерны, забор | Где находится промзона |
| Какой формы крыша, где ворота, где окна | Есть ли у дома дверь (это `flags` в данных) |

**Правило-мнемоника:** PCG — это художник, который пришёл на готовую площадку. Он решает,
*как* всё выглядит, но не решает, *что* здесь будет.

---

## 2. Правило №1: граф отдаёт данные, а не объекты

```
НЕЛЬЗЯ:  граф ──► спавнит актёров "Дом_1", "Дом_2" ...
                  (у клиента и сервера разные имена и номера → синхронизировать нечего)

НУЖНО:   граф ──► список записей ──► СЕРВЕР: сущности с ID, лут, двери, коллизия
                                 └──► КЛИЕНТ: меши, детали, декор
```

**Пример плохо:** граф создаёт актёр «Ангар_37» на клиенте и «Ангар_41» на сервере. Сервер
говорит «дверь ангара №87 открыта» — клиент не знает, о каком из его ангаров речь.

**Пример хорошо:** граф отдаёт запись `{ kind: "ангар", pos: (12043, 8702, 10234),
yaw: 16384, variantSeed: 9902 }`. ID считается как `Hash64(seed, cx, cy, kind, localIndex)` —
одинаковый у обеих сторон. Дальше сервер и клиент работают с одним и тем же объектом №87.

### 2.1 Что именно является «выходом» графа

| Выход | Куда попадает |
|---|---|
| Раскладка структур | В блок `structures` данных участка (сервер → клиент) |
| Декоративные инстансы (трава, листва, камни) | Только в память клиента, никуда не передаётся |
| Внутренние детали здания (плинтусы, провода, мусор) | Только клиент, из `variantSeed` |

## 3. Правило №2: вход графа — только наши данные

| Вход | Разрешено | Источник |
|---|---|---|
| Высоты участка | ✅ | Наш генератор (готовый массив) |
| Маски (лес, камень, грязь, разрешение) | ✅ | Наш генератор (массив на CPU) |
| Раскладка структур от сервера | ✅ | Данные участка |
| Генплан (реки, дороги, границы) | ✅ | Генплан |
| Физика (луч в коллизию, «найти поверхность») | ❌ **запрещено** | — |
| RVT, текстуры с видеокарты | ❌ **запрещено** | — |
| Время, «случайный» сид по умолчанию | ❌ **запрещено** | — |

### 3.1 Почему запрещена физика

Типовой узел PCG ищет землю «лучом вниз по коллизии». Коллизия готовится **асинхронно**:
в момент генерации её может ещё не быть, или она будет в другой версии. Результат зависит от
того, когда именно граф запустился — а у клиента и сервера это разные моменты.

**Результат:** объекты падают в точку (0,0,0) или на другую высоту, клиент и сервер расходятся.

**Замена:** свой узел `UPCGTerrainQuery` — берёт высоту прямо из массива высот (бинарный поиск
по сетке + билинейное смешивание, см. `04-terrain-and-collision.md`).

### 3.2 Почему запрещён RVT и вообще GPU

- RVT обновляется на видеокарте с задержкой в кадр-два;
- чтение результата обратно на CPU — дорого и асинхронно;
- вычисления на GPU в дробных числах не одинаковы на разных видеокартах.

**Результат:** «трава выросла по прошлому кадру масок» и разные миры у игроков с разными GPU.

**Замена:** граф читает **тот же массив масок**, из которого мы заливаем RVT. Раскраска и
растительность гарантированно совпадают.

```
массивы масок (CPU) ──┬──► RVT (красит землю)
                      └──► наш узел PCG (ставит растительность)
```

## 4. Наши узлы (собственный слой)

Все узлы живут в модуле проекта и регистрируются в PCG. Встроенные узлы, читающие физику/GPU,
заменяются нашими.

| Узел | Что делает |
|---|---|
| `UPCGTerrainHeight` | Высота и нормаль в точке (из массива высот, без физики) |
| `UPCGTerrainMask` | Значение маски (лес/камень/грязь/разрешение) в точке |
| `UPCGWaterMask` | Близость к воде, расстояние до русла, «затоплено ли» |
| `UPCGRandomInt` | Целое случайное число от `(сид, назначение, участок, ключ)` |
| `UPCGDensityTest` | Проверка плотности в целых числах (`0…10000`) |
| `UPCGStructureInput` | Принимает раскладку структур от сервера как входные данные |
| `UPCGInstancesToRecords` | Превращает точки в записи данных (позиция в см, поворот в `uint16`, сид варианта) |
| `UPCGOutputHash` | Считает хеш выходных записей участка (для проверки одинаковости) |

> ⚠️ Встроенные узлы `StaticMeshSpawner`, `SplineSampler`, `Difference`, `Intersection` — можно
> использовать для **косметики**, но не для решений. Для не-косметики — только свои узлы.

## 5. Режимы работы графа

| Режим | Кто | Что делает | Что отключено |
|---|---|---|---|
| `Server` | Сервер | Композиция структур → данные | Меши, инстансы, декор, RVT |
| `Client` | Клиент | Внешний вид + декор → инстансы | Запись раскладки (читает с сервера) |
| `EditorPreview` | Редактор | Просмотр и отладка | — |

Режим задаётся **параметром графа** (`UPCGGraphParameters`), а не отдельными графами: так
структура композиции гарантированно одна и та же.

## 6. Запреты (чек-лист при ревью графов)

1. ❌ Граф спавнит актёров (на сервере — в принципе; на клиенте — только для косметики).
2. ❌ Граф читает физику (`Surface Sampler`, трейсы, «найти поверхность»).
3. ❌ Граф читает RVT/текстуры с GPU.
4. ❌ Граф использует `FMath::Rand` / `FRandomStream` по цепочке.
5. ❌ Граф запускается без явно заданного сида.
6. ❌ Граф сравнивает дробные пороги с дробными значениями.
7. ❌ Граф зависит от порядка выполнения (слияние «кто первый», глобальные свёртки).
8. ❌ Граф использует «иерархическую» / распределённую генерацию PCG (порядок не гарантируется).
9. ❌ Граф решает, *что* ставить (только *как*).

## 7. Случайность внутри PCG

Каждому графу задаётся сид из нашей счётной формулы:

```
сид_графа = Hash64(сид_мира, назначение_графа, cx, cy)
```

Даже если внутри графа используется стандартный генератор PCG, он получает фиксированный сид и
даёт одинаковый результат (этот генератор устроен на целых числах и переносим). Опасность — не в
нём, а в **дробных порогах**, поэтому:

- плотности задаются целыми `0…10000`;
- сравнение — через `UPCGDensityTest` (`случайное % 10000 < плотность`);
- поворот и размеры — целые (сантиметры, `uint16` для углов).

## 8. Правило границ: ничего не решается между участками

> **Всё, что выходит за границы участка, обязано быть решено в генплане.**

**Пример.** «Промзона примыкает к железной дороге, стоит вдоль шоссе, не пересекает реку» —
это глобальное решение (нужна вся карта) → **генплан**: «промзона №3: центр здесь, примыкание
к ж/д здесь, ось вдоль шоссе 37°».

Внутри промзоны PCG решает локальное: «склады вдоль внутренней дороги шагом 40 ± 5 м, ворота
к дороге, цистерны в юго-западном углу». Это чисто локальные правила в пределах одного участка
(или его части).

**Почему нельзя иначе:** участок A не знает, что поставил участок B. Если разрешить объектам
договариваться через границу, результат начнёт зависеть от порядка генерации — а он у клиента
и сервера разный.

## 9. Проверка одинаковости

| Проверка | Как | Критерий |
|---|---|---|
| Хеш выхода графа | `UPCGOutputHash` → в `structures.hash` | Два прогона на одном участке — одинаковый хеш |
| Независимость от физики | Прогон до готовности коллизии и после | Одинаковый хеш |
| Клиент ↔ сервер | Сравнение хешей при подключении | Совпало (иначе — аварийная досылка данных) |
| Независимость от порядка | Прогон участков в разном порядке | Одинаковый хеш |

---

## 10. Производительность

| Мера | Значение |
|---|---|
| Бюджет графа на участок | ≤ 3 мс (клиент, воркер-поток) |
| Декор только рядом | Инстансы травы/листвы — не дальше 300–500 м |
| Кеш | Результат по `(сид, cx, cy, graphVersion)`; повторный вход — из кеша |
| Не считать за пределами визуала | Стриминг вызывает графы только для нужных участков |
