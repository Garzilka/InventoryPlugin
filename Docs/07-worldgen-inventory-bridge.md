# 07. Мост «генерация мира ↔ инвентарь и лут»

**Статус:** 🟡 предложение (контракт стыка, требует проверки кодом)
**Связано:** [`02-data-contract.md`](02-data-contract.md), [`01-determinism.md`](01-determinism.md),
[`06-inventory-ecosystem.md`](06-inventory-ecosystem.md), ADR-0004, ADR-0008

Документ отвечает на один вопрос: **как процедурный мир и готовый плагин инвентаря стыкуются так,
чтобы не появилось второго источника правды.**

---

## 1. Исходная точка

| Сторона | Что уже есть | Чего нет |
|---|---|---|
| Генерация мира | План (`00`–`05`), ADR; код не начат | Ни одной строки C++ по миру, нет `structures[]` в рантайме |
| Инвентарь (`InventoryEcosystem`) | 40 тыс. строк рабочего кода: предметы, инвентари, сеть, лут, торговля, редакторы | Нет детерминизма, нет связи с участком, нет UI |

Отсюда правило стыка: **мир решает «что где стоит», инвентарь решает «что внутри и как это
переносится»**. Ни один из них не должен решать за другого.

---

## 2. Кто за что отвечает

| Вопрос | Кто отвечает | Где живёт |
|---|---|---|
| Где стоит контейнер / ящик / труп | Генерация мира (сервер) | `structures[]` в данных участка (`02` §4.4) |
| Какой тип лута у этого контейнера | Генерация мира (при раскладке) → GUID лут-таблицы | Поле в записи структуры (например `lootGuid`) |
| Что конкретно внутри | Инвентарь (сервер) по детерминированному RNG | Инвентарь контейнера, репликация состояния |
| Как предмет выглядит в мире | Инвентарь (`UBaseWorldItemService`, `ABaseItemActor`) | Актёр как представление, не как источник правды |
| Что игрок забрал/положил | Инвентарь (сервер) + правки (`Tier C`) | `FInventorySave` контейнера в `UBaseLootManager` |
| Когда лут респавнится | Инвентарь (`EGenerationLootType`) + правило мира | `TimeToRestart`, серверное время мира |

## 3. Поток данных

```
seed ──► ГЕНПЛАН ──► раскладка структур участка (сервер)
                          │  запись: { kind=ящик, pos, yaw, variantSeed, flags, lootGuid, id }
                          ▼
                    СЕРВЕР: спавн ABaseContainer
                          │  GUID = StableLootGuid(id) — без NewGuid!
                          ▼
                    СЕРВЕР: ULootWorldSubSystem::GenerateItems(RngCtx, Settings, Owner)
                          │  RNG = Hash64(seed, Purpose::Loot, cx, cy, containerId)
                          ▼
                    СЕРВЕР: инвентарь контейнера = предметы (UObject)
                          │  репликация: сабобъекты + COND_OwnerOnly для персональных
                          ▼
                    КЛИЕНТ: UI контейнера, ABaseItemActor для выпавших предметов
```

Ключевое: **клиент не считает лут вообще**. Он получает уже созданные предметы как состояние.
Это снимает вопрос «одинаковый ли лут у всех» и совпадает с ADR-0004 (данные, а не вычисления).

---

## 4. Стабильные ID: от структуры к контейнеру

В `02-data-contract.md` ID структуры уже определён:

```
id = Hash64(seed, cx, cy, kind, localIndex)
```

Плагину нужен **`FName`-GUID** (`ULootObjectGUID::GUID`), а не `uint64`. Поэтому вводим
детерминированное преобразование:

```cpp
// 16 hex-символов: читаемо в ассетах и логах, без коллизий на нашей шкале
static FName StableLootGuid(uint64 StructureId)
{
    return FName(*FString::Printf(TEXT("%016llX"), StructureId));
}
```

Правила:

1. **Запрещено** `FGuid::NewGuid()` для всего, что родилось из процедуры (сейчас именно так
   работает `ULootObjectGUID::AddToLootSystem()` — годится только для ручных объектов).
2. GUID обязан быть воспроизводим из (сид, участок, индекс) — тогда перезапуск сервера находит ту
   же запись в сохранении.
3. Для ручных «красивых мест» GUID остаётся авторским (`NewGuid` в редакторе) — допустимое
   исключение, но такие объекты не должны встречаться в процедурных участках.
4. Если у контейнера нет своего лут-ассета, GUID можно не создавать: `EGLT_None` = пусто.

## 5. Детерминированный лут (главная правка)

### 5.1 Что не так сейчас

`ULootWorldSubSystem` использует `FMath::RandRange` в пяти местах (шанс, вес строк, количество).
Порядок вызовов и число итераций зависят от данных, поэтому:

- сервер и клиент дадут разный лут, если считать на обеих сторонах;
- два запуска сервера с одним сидом дадут разный лут;
- сохранение нельзя проверить хешем.

### 5.2 Как надо

Ввести контекст случайности и запретить «голый» рандом в генерации:

```cpp
// Назначения — из реестра 01-determinism.md, диапазон 800–899 («внутренние детали, лут»)
enum class ELootPurpose : uint32
{
    BlockChance  = 800,  // прошёл ли блок вероятной генерации
    RowPick      = 801,  // выбор строки по весу
    Amount       = 802,  // количество предметов
    ItemVariant  = 803,  // вариант предмета (качество, патроны)
    RespawnDelay = 804,  // разброс времени респавна
};

struct FLootRngContext
{
    uint64 WorldSeed = 0;
    int32  ChunkX = 0;
    int32  ChunkY = 0;
    uint64 ContainerId = 0;   // = id структуры
    uint32 BlockIndex = 0;    // индекс блока в FGenerateSettings
};

uint32 LootRandom(const FLootRngContext& Ctx, ELootPurpose Purpose, uint32 Key)
{
    // Hash64 — из 01-determinism.md §2.2, только целые числа
    uint64 H = Hash64(Ctx.WorldSeed ^ (uint64)Purpose);
    H = Hash64(H ^ (uint64)(uint32)Ctx.ChunkX);
    H = Hash64(H ^ (uint64)(uint32)Ctx.ChunkY);
    H = Hash64(H ^ Ctx.ContainerId);
    H = Hash64(H ^ (uint64)Ctx.BlockIndex);
    H = Hash64(H ^ (uint64)Key);
    return (uint32)(H >> 32);
}

// Шанс — целые 0…10000, сравнение без float
bool Roll(const FLootRngContext& Ctx, ELootPurpose P, uint32 Key, int32 Chance10000)
{
    return (int32)(LootRandom(Ctx, P, Key) % 10000u) < Chance10000;
}
```

Изменения в плагине:

| Файл | Правка |
|---|---|
| `LootWorldSubSystem.h/.cpp` | `GenerateItems/GenerateItem/GenerateItemsData` получают `FLootRngContext`; все `FMath::RandRange` → `LootRandom` |
| `LootSystemData.h` | `float Percent` → `int32 Chance10000`; `float Weight` → `int32 Weight`; `float TimeToRestart` → `int32 Seconds` |
| `InventoryLibrary.h/.cpp` | `FInventoryItemData::Range` разыгрывается через переданный RNG (либо количество считается в `ULootWorldSubSystem`, а `MakeItems` остаётся детерминированным) |
| `BaseLootComponent` | передаёт контекст (участок/контейнер) от владельца |

### 5.3 Что остаётся случайным

- Отдача оружия, гильзы, декали, звуки — косметика, `FMath::Rand` допустим (клиент, на геймплей
  не влияет).
- Разброс времени респавна считается один раз на сервере и сохраняется, дальше берётся из
  сохранения, а не пересчитывается.

## 6. Что лежит в участке: два варианта хранения

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **A. Только раскладка структур** | В `structures[]` пишем `kind`, `pos`, `yaw`, `variantSeed`, `flags`, `lootGuid`, `id`; предметы внутри — состояние сервера | Совпадает с ADR-0004; данных на участок мало | Сервер обязан держать реестр «какие контейнеры уже созданы» |
| **B. Блок `entities[]` в данных участка** | Плюс отдельный блок «что лежит на земле» (id, класс, позиция, состояние) | Клиент может показать дроп без серверного спавна | Дублирование состояния: правки игроков всё равно отдельно; растёт формат |

**Рекомендация:** A + тонкий «реестр созданных сущностей» на сервере (ключ — `id` структуры).
Причина: предметы в мире — это **состояние**, а не генерация; попытка держать их в данных участка
приводит к тому же конфликту, что и «PCG спавнит актёров» (ADR-0004).

## 7. Жизненный цикл контейнера

```
УЧАСТОК: НЕТ
   │  сервер: пришли данные участка, раскладка построена
   ▼
УЧАСТОК: ДАННЫЕ ЕСТЬ → создаём контейнеры (только сервер), лут НЕ считаем
   │  игрок подошёл / открыл / первый вход (EGLT_BeginPlay)
   ▼
ЛУТ СОЗДАН (детерминированно из RNG-контекста или загружен из сохранения)
   │
   ▼
ИЗМЕНЁН ИГРОКОМ → FInventorySave уходит в UBaseLootManager (правка Tier C)
   │  участок выгружен
   ▼
КОНТЕЙНЕР УНИЧТОЖЕН, сохранение осталось (по GUID / id структуры)
```

Правила:

1. Контейнеры создаёт **только сервер**; клиент никогда не создаёт лут сам.
2. Лениво: лут считается при первом обращении, а не при загрузке участка (иначе 1000 контейнеров
   × генерация = фриз).
3. Уникальный лут (`bIsUniqueLoot`) требует персонального инвентаря (`UniqInventoryes`) и
   заполнения пустых `RegisterLoginPlayer` / `RegisterLogoutPlayer`.
4. При выгрузке участка контейнер уничтожается, состояние остаётся в `UBaseLootManager` игрока
   (сейчас так и сделано: `SaveDataFor` при изъятии).
5. Если контейнер никто не открывал — сохранение не создаётся, лут пересчитается тем же RNG.

## 8. Сохранения и правки (`Tier C`)

| Данные | Где хранится | Ключ | Кто пишет |
|---|---|---|---|
| Состояние контейнера | `UBaseLootManager::ContainerSaveData` (`SaveGame`) | `FName ContainerName` = GUID контейнера | Сервер |
| Время респавна | `FContainerData::TimeRestart` (сейчас `FDateTime`) | тот же | Сервер |
| Предметы на земле | правки игроков (`02` §6) | `id` сущности | Сервер |
| Инвентарь игрока | компоненты игрока (`UBaseLineInventory`) | — | Сервер |

Требования к стыку:

1. **Ключ сохранения — стабильный ID**, а не имя актёра (`GetFName()` меняется при стриминге).
2. **Время — целые секунды мира**, не `FDateTime`: реальные часы ломают воспроизводимость.
   В плагине это надо заменить.
3. **Канонический порядок** применения правок: по времени, затем по `id` (`02` §6.3).
4. Правки не могут менять генплан и раскладку структур (нельзя «передвинуть ящик» процедурно).

## 9. Сеть и бюджеты

| Что | Решение | Почему |
|---|---|---|
| Лут контейнера | Состояние от сервера, `COND_OwnerOnly` для персонального | Единый источник правды, нет расхождений |
| Инвентарь игрока | `COND_OwnerOnly` | Чужие сумки клиенту не нужны |
| Выпавшие предметы на земле | `ABaseItemActor` + `bOnlyRelevantToOwner` при необходимости | Экономия трафика |
| Торговля | `Server_OpenTrade_*` + репликация `FTradeState` | Авторитет сервера |
| Следы/эффекты | локально | Косметика |

Оценка трафика (грубая, для планирования):

- запись структуры ≈ 24 байта (`02` §4.4) → ~250 объектов на плотный участок ≈ 6 КБ;
- предмет в инвентаре: класс + `Amount` + сервисы → десятки байт; полный рюкзак (40 предметов)
  ≈ 2–4 КБ на одно изменение, поэтому мутации шлём по одной, а не «весь рюкзак».

## 10. Числа: единый язык мира и инвентаря

| Величина | Формат | Где используется |
|---|---|---|
| Позиция | `int32`, см | `structures[]`, актёры, лут-точки |
| Угол | `uint16` (65536 = 360°) | `yaw` структур, поворот контейнера |
| Вес | `int32`, граммы | `FDefaultItemData::Weight`, сумма по инвентарю |
| Шанс/плотность | `int32`, 0…10000 | лут-блоки, вероятности |
| Деньги | `int32`, минимальная единица валюты | торговля (`FCurrencyValue`) |
| Время | `int64`, миллисекунды мира | респавн, правки |

Правило-проверка из `01`: **если значение уходит в решение — оно целое.**

## 11. Этапы (предложение)

| Этап | Что делаем | Критерий готовности |
|---|---|---|
| **I-0** | Включить плагин, собрать Editor + Server, пройти по демо-карте | Проект собирается, персонаж ходит, инвентарь открывается |
| **I-1** | Детерминированный RNG лута + `LOOT_VERSION` | Два прогона с одним сидом дают одинаковый набор предметов; golden-хеш |
| **I-2** | GUID контейнеров из `id` структуры | Перезапуск сервера находит сохранение того же контейнера |
| **I-3** | Спавн контейнеров по `structures[]` (тестовая раскладка руками) | 100 контейнеров на 4 участках, лут ленивый, без фризов > 30 мс |
| **I-4** | Сохранение состояния контейнеров + правки игроков | Забрал предмет → рестарт → предмет не вернулся (кроме респавна) |
| **I-5** | UI: инвентарь, контейнер, экшен-меню, торговля | Игрок играет без консоли |
| **I-6** | Вес/объём, ограничения, тесты | Перегрузка работает; тесты зелёные |

## 12. Тесты, которые обязаны быть (следуя `01` §6)

1. `LootDeterminism`: один и тот же (сид, участок, контейнер) → одинаковый список предметов
   (сравнение хеша).
2. `LootIndependenceFromOrder`: контейнеры генерируются в разном порядке → хеши совпадают.
3. `GUIDStability`: `StableLootGuid(id)` не меняется между запусками и платформами.
4. `InventorySerializeRoundtrip`: сохранить → загрузить → состояние и `Amount` совпадают.
5. `TransferBetweenInventories`: предмет не может оказаться в двух инвентарях
   (`ParrentObject` ровно один).
6. `ServerAuthority`: клиент не может добавить предмет себе RPC-вызовом в обход проверки.
