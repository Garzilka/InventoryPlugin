# 04. Рельеф, меши и коллизия

**Статус:** 🟡 черновик v1 (цифры требуют замера на спайке)

Документ описывает, как из массива высот получается то, по чему ходит игрок, и как это
укладывается в бюджет кадра.

---

## 1. Из данных в треугольники

```
массив высот 257 × 257 (uint16)
        │
        ├──► меш для рендера: LOD 0 = 1 м, LOD 1 = 2 м, … LOD 5 = 32 м
        │
        └──► коллизия: LOD 1 = 2 м (вблизи игрока)
```

- Сетка участка: 256 × 256 м, 257 × 257 вершин (шаг 1 м).
- Треугольники: 256 × 256 × 2 = **131 072** при LOD 0.
- Граничный ряд вершин у соседей **совпадает по значению** (мы дублируем ряд), поэтому щелей
  в геометрии нет даже без сглаживания.

---

## 2. Детализация (LOD) и «юбки»

### 2.1 Зачем LOD

Вблизи нужен шаг 1 м (иначе дорога шириной 6 м выглядит рубленой), вдали — не нужен.
Каждый шаг удвоения уменьшает количество треугольников **в 4 раза**.

| LOD | Шаг сетки | Треугольников на участок | Дистанция (пример) |
|---|---|---|---|
| 0 | 1 м | 131 072 | 0–200 м |
| 1 | 2 м | 32 768 | 200–400 м |
| 2 | 4 м | 8 192 | 400–800 м |
| 3 | 8 м | 2 048 | 800–1500 м |
| 4 | 16 м | 512 | 1500–2500 м |
| 5 | 32 м | 128 | 2500+ м |

Для дальних дистанций участки **объединяются** в супер-участки 1024 × 1024 м, чтобы не рисовать
сотни мелких мешей (иначе упрёмся в количество вызовов отрисовки, а не в треугольники).

### 2.2 Юбки (skirt)

**Проблема.** На стыке участков с разной детализацией вершины не совпадают, между ними
появляются тонкие щели — в них видно небо или пустоту.

```
вид сбоку на стык:

  участок A (сетка 1 м)              участок B (сетка 8 м)
   /\  /\  /\  /\   |   |                |\        /\        /\
                    |   | <- щель        |
                    |   |    (пустота)   |
              ______|___|________________|______
              |                                |  <- юбка
              |________________________________|     (шторка вниз 3 м)
```

**Решение.** По периметру участка добавляем вертикальную «шторку» — крайние вершины дублируются
с понижением на 3 м вниз. Щель закрывается той же землёй, игрок видит землю, а не пустоту.

Юбка — это «страховка»: она скрывает любые остаточные расхождения (округления, разные LOD).

### 2.3 Обязательные правила меша

| Правило | Почему |
|---|---|
| Граничный ряд вершин = точно значение соседа | Нет щелей |
| Юбка 3 м по периметру | Скрывает T-стыки разных LOD |
| Нормали считать по сетке высот, а не по треугольникам | Не будет «гранёных» склонов и швов в освещении |
| Перестроение меша только на воркер-потоке | Нельзя тратить кадр на 66 тыс. вершин |
| В дальнем LOD участки объединять в супер-участки | Экономия вызовов отрисовки |

## 3. Коллизия рельефа (выбран вариант «меш вблизи»)

### 3.1 Что делаем

| Шаг | Описание |
|---|---|
| 1 | Из высот строим треугольники на сетке **2 м** (129 × 129 вершин, 32 768 треугольников) |
| 2 | Отдаём движку с асинхронной готовкой (`bUseAsyncCooking`) — физика готовится в фоне |
| 3 | Держим коллизию только в радиусе **400–600 м** от игроков |
| 4 | Участок получает состояние `КОЛЛИЗИЯ ГОТОВИТСЯ` → `ГОТОВ` |

### 3.2 Почему сетка 2 м, а не 1 м

| | 1 м | 2 м |
|---|---|---|
| Вершин | 66 049 | 16 641 |
| Треугольников | 131 072 | 32 768 |
| Память физики на участок | ~10–15 МБ | ~3–4 МБ |
| Время готовки | десятки мс | единицы мс |
| Заметность для игрока | — | почти нет (на склонах до ~10–20 см) |

Игрок ходит по земле, а не «щупает» её микрорельеф, поэтому 2 м достаточно. Если на склонах
появится заметное «плавание» — рядом с игроком можно переключаться на 1 м.

## 4. Прямой расчёт по высотам (без физики)

Второй способ узнать «где земля» — посчитать по массиву. Используется там, где физика либо
недоступна (далеко), либо избыточна (пули, обзор ИИ, проверка «можно ли тут построить»).

### 4.1 Высота в произвольной точке (билинейно)

```
Точка между узлами: (10,10) = 100 см, (11,10) = 102 см, на 30% пути к правому:

высота = 100 · 0.7 + 102 · 0.3 = 100.6 см
```

Если точка внутри клетки — смешиваем четыре узла по расстоянию:

```
h = h00·(1−tx)·(1−ty) + h10·tx·(1−ty) + h01·(1−tx)·ty + h11·tx·ty
```

Результат — целое в сантиметрах (`int32`), считается за наносекунды, не требует ни физики,
ни памяти.

### 4.2 Луч «есть ли земля на пути» (баллистика, видимость)

Идём по клеткам сетки вдоль луча (алгоритм Брезенхэма/DDA), на каждой проверяем высоту:

```
для каждой клетки вдоль луча:
    если высота_клетки > высота_луча_в_этой_точке:
        попадание (земля)
```

Работает на любой дистанции (до 3 км и дальше), одинаково у клиента и сервера, не зависит от
готовности физики.

### 4.3 Что чем считаем

| Задача | Чем |
|---|---|
| Ходьба игрока, падение предметов, машины | **Коллизия** (тримеш 2 м, радиус 400–600 м) |
| Пули, осколки, видимость, обзор ИИ | **Прямой расчёт** по высотам (на любой дистанции) |
| Высота для PCG и растительности | **Прямой расчёт** (запрещено читать физику) |
| «Можно ли тут ставить/копать» | **Прямой расчёт** + маски |
| Сетка проходимости (будущее) | **Прямой расчёт** + маски + контуры зданий |
| Стены, двери, крыши, техника, ящики | **Обычная физика UE** (коллизия из ассетов) |

## 5. Состояния, готовность и «не пускать в неготовое»

Асинхронная готовка означает: меш уже видно, а стоять на нём ещё нельзя. Это классический баг
«провалился в пустоту на краю загрузки».

**Правила:**

1. Коллизия готовится **с опережением**: на 2–3 участка впереди направления движения игрока.
2. Пока участок не `ГОТОВ`, логика (спавн, телепорт, строительство) в него не пускает.
3. На клиенте неготовый участок для игрока — «мягкая стена» (40–100 мс ожидания).
4. На сервере неготовый участок — отказ в перемещении (с повторной проверкой).

**Проверка на здравый смысл:** игрок бежит 6 м/с, участок 256 м пересекает за 42 секунды.
Время готовки коллизии — единицы миллисекунд. Запас огромный, если готовить заранее.

---

## 6. Почему не предрасчитываем коллизию всего мира

| Вариант | Память (мир 16 × 16 км = 4096 участков) | Трафик | Гибкость |
|---|---|---|---|
| Предрасчёт всего мира (2 м) | ~14 ГБ | 3.5 МБ на каждый новый участок | Меняем генератор — пересчитывать всё |
| Рантайм + кеш в пределах сессии | ~100 МБ (25 участков) | 0 | Ничего не надо |

Дополнительно: готовую физику UE нельзя «загрузить» из присланного блока — в рантайме есть
только путь «построить меш и попросить движок приготовить физику». То есть предрасчёт сводится
к предрасчёту треугольников, которые клиент и так получает из высот бесплатно.

---

## 7. Подводные камни

| Камень | Как обходим |
|---|---|
| Провал в пустоту на краю загрузки | Правило «только `ГОТОВ`» + подготовка с опережением |
| Плавающий персонаж / провал на 2 м коллизии | Нормали и освещение считаем по 1 м сетке, коллизия 2 м; при жалобах — 1 м рядом с игроком |
| Трещины на стыке LOD | Юбки 3 м + одинаковый LOD на группе 2 × 2 |
| Мерцание (z-fighting) декора с землёй | Приподнимаем декор на 2–3 см + `Pixel Depth Offset` |
| Дорогие вызовы отрисовки вдали | Объединение в супер-участки 1024 м на дальних LOD |
| Память мешей | LOD 0 только в радиусе ~200–400 м |
| Перестроение меша в кадре | Только воркер-поток, готовый буфер отдаём в кадр |

## 8. Спайки (проверить до больших объёмов)

| № | Проверка | Критерий «прошло» |
|---|---|---|
| 1 | Один участок: высоты → меш → коллизия, персонаж ходит | Провалов нет; коллизия ≤ 10 мс; ≤ 4 МБ |
| 2 | Два соседних участка с разными LOD | Щелей не видно (юбки работают) |
| 3 | Пробег 1 км по стримящимся участкам | Нет фризов > 30 мс; нет провалов |
| 4 | Баллистика на 800 м по высотам | Попадание совпадает с видимой поверхностью |
| 5 | Две генерации одного участка | Высоты побайтово совпадают |
